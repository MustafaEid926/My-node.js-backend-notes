
## **مقدمة: تعديل مخطط لمجموعة موجودة مسبقاً**
في الدروس السابقة، تعلمنا كيف نقوم بفرض مخطط للتحقق من صحة البيانات (**Schema Validation**) أثناء إنشاء المجموعة لأول مرة باستخدام الدالة `createCollection`. 
ولكن في بيئات العمل الحقيقية، قد تواجه سيناريو تكون فيه المجموعة (**Collection**) موجودة مسبقاً (تم إنشاؤها في الماضي)، وتحتاج كمهندس بيانات إلى إضافة مخطط جديد لها أو تعديل مخططها الحالي. 

---

## **الأداة الأساسية: دالة `runCommand` ومُعدّل المجموعة `collMod`**
لتعديل مجموعة موجودة بالفعل (مثل مجموعة `users` أو `products`)، لا يمكننا استخدام دالة الإنشاء، بل يجب أن نستخدم دالة عامة لتنفيذ الأوامر تُسمى **`runCommand`** والتي يتم استدعاؤها عبر الكائن `db`.

### **آلية عمل الدالة `runCommand`**
*   تستقبل هذه الدالة كائناً (**Object**) نحدد بداخله الإعدادات والخصائص التي نريد تعديلها.
*   **الخاصية ==`collMod`==:** (وهي اختصار لـ **Collection Modifier** أو مُعدّل المجموعة). نستخدم هذه الخاصية داخل الكائن لتحديد اسم المجموعة التي نود تعديلها (مثال: `collMod: "users"`) .
*   **الخاصية ==`validator`==:** تماماً كما فعلنا عند إنشاء المجموعة، نستخدم هذه الخاصية لتعريف المخطط الجديد أو المعدل باستخدام مُشغّل **`jsonSchema$`**.

---

## **المشكلة: السماح بإدراج الحقول الإضافية (Additional Properties)**
في المخطط السابق الذي طبقناه على مجموعة `users`، قمنا بتحديد حقول إجبارية (`name`, `email`, `address`) وحقل اختياري (`gender`). 
*   **القصور في المخطط القديم:** كان هذا المخطط يسمح للمستخدم بإدراج حقول إضافية عشوائية لم يتم تعريفها مسبقاً (مثل حقل العنوان `title`، أو السعر `price`)، وكانت قاعدة البيانات تقبل الDocument وتدرجه دون مشاكل .
*   **الهدف الهندسي:** نحن نريد تطبيق صرامة مطلقة بحيث لا يُسمح بإدراج أي حقل في الDocument بخلاف الحقول الأربعة المحددة في المخطط.

---

## **الحل: تقييد المخطط عبر خاصية `additionalProperties`**
لمنع إدراج أي حقول إضافية عشوائية، توفر لنا **MongoDB** خاصية هامة جداً تُسمى ==**`additionalProperties`**==
*   يتم إضافة هذه الخاصية داخل كائن المخطط وتعيين قيمتها إلى المنطقية **`false`**.
*   هذا يعني ببساطة: "لا تسمح بأي خصائص إضافية بخلاف الخصائص (properties) المعرفة صراحةً في هذا المخطط".

---

## **المشكلة المعمارية الخفية: خطأ المعرف التلقائي (`id Field Error_` )**
عند تطبيق خاصية `additionalProperties: false` ومحاولة إدراج Document يطابق المخطط تماماً (يحتوي فقط على `name`, `email`, `address`)، ستتفاجأ بأن **MongoDB** سترفض العملية وتُرجع خطأ برمجياً (**MongoDB Server Error**)! .

### **لماذا حدث هذا الخطأ؟**
*   عند إدراج أي Document جديد، تقوم **MongoDB** تلقائياً بإنشاء وإضافة حقل فريد يُسمى **`id_`** لتمييز هذا الDocument .
*   بما أنك عينت `additionalProperties` إلى `false`، فإن محرك قاعدة البيانات سيعتبر حقل `id_` (الذي يحاول هو نفسه إضافته) حقلاً "إضافياً" غير مصرح به، لأنه غير مكتوب صراحةً داخل المخطط الخاص بك، وبالتالي تفشل عملية التحقق (**Validation Failed**).

### **كيفية حل هذه المشكلة؟**
لحل هذا التعارض، يجب أن تقوم بتعريف حقل **`id_`** بشكل صريح (**Explicitly**) داخل كائن الخصائص (`properties`) في مخططك، وتحديد نوع البيانات الخاص به كـ **`objectId`**. بهذه الطريقة ستعرف قاعدة البيانات أن هذا الحقل مصرح به ولن ترفضه.

---

## **التطبيق العملي: الكود الشامل لتحديث المخطط**
إليك الكود البرمجي الكامل الذي كتبه المحاضر لتعديل مجموعة `users`، والذي يشمل خاصية `additionalProperties` وحل مشكلة حقل `id_` :

```javascript
db.runCommand({
  collMod: "users", // تحديد المجموعة المراد تعديلها
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "email", "address"],
      additionalProperties: false, // منع أي حقول غير المعرفة بالأسفل
      properties: {
        
        // 1. تعريف حقل المعرف لتجنب خطأ الإدراج التلقائي
        _id: {
          bsonType: "objectId"
        },
        
        // 2. الحقول الأساسية
        name: {
          bsonType: "string"
        },
        email: {
          bsonType: "string"
        },
        address: {
          bsonType: "object",
          required: ["city", "country"], // يمكن إضافة قيود داخلية للDocument المضمن
          properties: {
            street: { bsonType: "string" },
            city: { bsonType: "string" },
            country: { bsonType: "string" }
          }
        },
        gender: {
          bsonType: "string"
        }
        
      }
    }
  }
})
```
عند تنفيذ هذا الكود، سيتم تحديث المخطط بنجاح على المجموعة الموجودة.

## **اختبار التحقق من صحة البيانات بعد التعديل (Testing the Schema)**
لتأكيد فاعلية المخطط الجديد، سنقوم بإجراء الاختبارات التالية:
1.  **محاولة إدراج Document يحتوي على الحقول (`name`, `email`, `address`, `title`, `price`):**
    *   **النتيجة:** طرح الخادم خطأ برمجي (**Validation Error**) ورفض الإدراج، لأن حقلي `title` و `price` غير معرفين، لأن خاصية `additionalProperties` تمنعهما .
2.  **محاولة إدراج Document نظيف يحتوي فقط على (`name`, `email`, `address`):**
    *   **النتيجة:** تم إدراج الDocument بنجاح. تم قبول البيانات وتوليد حقل `id_` التلقائي دون أي مشاكل بفضل تحديث المخطط.
