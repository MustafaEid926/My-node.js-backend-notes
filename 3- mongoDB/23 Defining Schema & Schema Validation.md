
## **مقدمة: أهمية المخطط (Schema) في التطبيقات الحقيقية**
كما تعلمنا سابقاً، فإن العمل مع مجموعات (**Collections**) لا تمتلك مخططاً مسبقاً (**Predefined Schema**) قد يكون أمراً مرهقاً جداً وصعب الإدارة عند بناء تطبيقات حقيقية (**Real-world Applications**).
*   **المشكلة في انعدام المخطط:** في المجموعة التي لا تمتلك مخططاً، يمكنك إدراج أي نوع من المستندات (**Documents**). على سبيل المثال، يمكنك إدراج Document يخص مستخدماً (**User Document**) داخل مجموعة مخصصة للمنتجات (**Products Collection**)، ولن تعترض **MongoDB** على ذلك نهائياً.
*   **الحل:** عندما نقوم بتعريف مخطط (**Schema**) للمجموعة، فإننا نضمن أنه لن يتم إدراج أي Document في هذه المجموعة إلا إذا كان يتبع ويطابق هذا المخطط بدقة. ولذلك، يجب علينا دائماً تحديد نوع من المخططات لمجموعاتنا.

---

## **طرق تعريف المخطط (Ways to Define a Schema)**
هناك طريقتين رئيسيتين لتعريف المخطط:
1.  **أثناء الإنشاء الصريح (Explicit Creation):** تعريف المخطط عند إنشاء المجموعة الجديدة لأول مرة (وهو ما تركز عليه هذه المحاضرة).
2.  **على مجموعة موجودة مسبقاً (Existing Collection):** تعديل مجموعة حالية لتعريف مخطط لها (سيتم شرحه في المحاضرة القادمة) .

---

## **خطوات إنشاء مجموعة بمخطط محدد (Creating Collection with a Schema)**

### **1. تجهيز بيئة العمل (Preparation)**
للبدء ببيئة نظيفة، سنقوم بحذف مجموعة `users` القديمة باستخدام دالة الحذف `()drop` كالتالي: `()db.users.drop`.
للتأكد من الحذف، استخدم الأمر `show collections` الذي أظهر المجموعتين `orders` و `products` فقط.

### **2. استخدام دالة (createCollection)**
لإنشاء المجموعة بشكل صريح، نستخدم الدالة `createCollection` على كائن قاعدة البيانات `db`.
*   **المعامل الأول (First Argument):** هو اسم المجموعة المراد إنشاؤها (في حالتنا `"users"`).
*   **المعامل الثاني (Second Argument):** هو كائن خيارات اختياري (**Optional Options Object**). (ملاحظة: استخدمنا هذا الكائن سابقاً لإنشاء المجموعات المقيدة **Capped Collections** عبر تحديد خصائص مثل `capped`, `size`, و `max`).
*   في هذا الدرس، لن ننشئ مجموعة مقيدة، بل سنستخدم هذا الكائن لتعريف مخطط دقيق باستخدام خاصية **`validator`**.

---

## **هيكلة كائن التحقق (The `validator` Object Structure)**
الخاصية **`validator`** هي المسؤولة عن فرض شروط التحقق على الDocumentات. نمرر لها كائناً يحتوي على خصائص متسلسلة لتعريف المخطط:

### **1. مُشغّل مخطط جافا سكريبت (`jsonSchema$`)**
داخل كائن الـ `validator`، يجب أن نحدد نوع المخطط الذي نريد تعريفه باستخدام الدرايفر **`jsonSchema$`** . نقوم بإسناد كائن لهذا الدرايفر لنبدأ بوضع القواعد.

### **2. تحديد نوع البيانات الأساسي (`bsonType`)**
أول خاصية داخل `jsonSchema$` هي **`bsonType`**. وبما أننا نريد إدراج مستندات (**Documents**) داخل الCollection ، والDocument في جوهره هو عبارة عن كائن (**Object**)، فيجب أن نحدد النوع كالتالي: `bsonType: "object"` .

### **3. الحقول الإجبارية (`required`)**
تأخذ هذه الخاصية مصفوفة (**Array**) نحدد بداخلها أسماء الحقول التي يجب أن تتواجد **إجبارياً** في كل Document يتم إدراجه في هذه المجموعة . 
*   **مثال:** `required: ["name", "email", "address"]`.

### **4. خصائص الحقول (`properties`)**
نستخدم كائن **`properties`** لتعريف الحقول (سواء كانت إجبارية أو اختيارية)، وتحديد نوع البيانات (**Data Type**) المسموح به لكل حقل، بالإضافة إلى إمكانية وضع رسائل خطأ مخصصة:
*   **تحديد النوع:** نستخدم `bsonType` لتعريف نوع كل حقل (مثل `string`, `int`.. إلخ) .
*   **رسائل الوصف/الخطأ (`description`):** تُستخدم هذه الخاصية لإظهار رسالة توضيحية للمستخدم في حال لم يقم بإدخال الحقل الإجباري، أو في حال أدخل قيمة بنوع بيانات خاطئ. (مثلاً إذا أدخل رقماً في حقل نصي) .

### **التطبيق العملي: الكود الشامل لتعريف المخطط (Schema Code Block)**
 إليك الهيكلة البرمجية الكاملة لإنشاء مجموعة `users` مع المخطط:

```javascript
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object", // الDocument عبارة عن كائن
      required: ["name", "email", "address"], // الحقول الإجبارية
      properties: {
        
        name: {
          bsonType: "string",
          description: "name is a required text field"
        },
        
        email: {
          bsonType: "string",
          description: "email is a required text field"
        },
        
        // حقل العنوان عبارة عن Document مضمن (Embedded Document)
        address: {
          bsonType: "object",
          description: "address is a required field",
          properties: { // تعريف الحقول الفرعية داخل الDocument المضمن
            street: { bsonType: "string" },
            city: { bsonType: "string" },
            country: { bsonType: "string" }
          }
        },
        
        // حقل اختياري (لم يتم إدراجه في مصفوفة required)
        gender: {
          bsonType: "string"
        }

      }
    }
  }
})
```
عند تنفيذ هذا الكود في **Mongo Shell**، سيرجع الخادم استجابة `{"ok": 1}`، مما يعني أنه تم إنشاء المجموعة وتطبيق المخطط عليها بنجاح* .

## **اختبار التحقق من صحة البيانات (Testing Schema Validation)**
لفهم كيف تقوم **MongoDB** بفلترة البيانات، سنقوم بإجراء عدة اختبارات باستخدام الدالة `insertOne`:

### **الاختبار الأول: تجاوز حقل إجباري (Missing Required Field)**
*   **العملية:** سنحاول إدراج Document يحتوي على (الاسم، البريد الإلكتروني، والجنس)، لكننا سنتعمد تجاهل حقل العنوان `address` (وهو حقل إجباري).
*   **النتيجة:** رفضت **MongoDB** العملية وطرحت خطأ برمجياً (**Validation Error**) يوضح أن خاصية `address` مفقودة . **لم يتم إدراج الDocument**.

### **الاختبار الثاني: إدخال نوع بيانات خاطئ (Wrong Data Type)**
*   **العملية:** تم توفير حقل العنوان بنجاح (بشكل Document متداخل يحتوي على `street`, `city`, `country`). ولكن، تم تعيين قيمة رقمية (`12345`) لحقل الاسم `name` بدلاً من قيمة نصية (**String**).
*   **النتيجة:** طرح النظام خطأ مجدداً لأن نوع البيانات لم يتطابق (`type did not match`). حقل الاسم يتوقع `string` ولكنه استلم عدد صحيح (**Integer**) . **لم يتم إدراج الDocument**.

### **الاختبار الثالث: إدراج Document صالح (Valid Document)**
*   **العملية:** تم إرسال الDocument بجميع الحقول الإجبارية، وتم التأكد من أن جميع القيم تطابق أنواع البيانات المحددة في المخطط (جميعها نصوص وDocumentات مضمنة صحيحة).
*   **النتيجة:** لم يظهر أي خطأ، وتم إدراج الDocument بنجاح في مجموعة `users` .

## **سلوك (MongoDB) مع الحقول الإضافية غير المعرفة**
سنجري اختباراً رابعاً بالغ الأهمية لكشف السلوك الافتراضي لعملية التحقق:
*   **العملية:** إدراج Document يحتوي على كافة الحقول الصحيحة السابقة، ولكنه أضاف حقلاً جديداً لم يتم ذكره إطلاقاً في المخطط، وهو حقل العمر (`age: 28`).
*   **المفاجأة:** تم قبول الDocument وتم إدراجه بنجاح داخل المجموعة!.

### **تفسير السلوك (?Why did it insert the document)**
*   **القاعدة الافتراضية:** المخطط الذي تم تعريفه يفرض شروطه بصرامة على الحقول المذكورة فيه فقط (يتأكد من وجود الحقول الإجبارية وصحة أنواعها). ولكنه، بشكل افتراضي، **يسمح بوجود حقول إضافية (Additional Fields)** لم يتم تعريفها في المخطط .

### **كيف نمنع الحقول الإضافية؟ (Restricting Additional Properties)**
*   إذا كنت تريد تطبيق صرامة مطلقة بحيث **يُمنع منعاً باتاً** إدراج أي حقل لم يتم تعريفه مسبقاً في كائن الـ `properties`، فيجب عليك استخدام خاصية إضافية تُسمى **`additionalProperties`** وتعيين قيمتها إلى **`false`**.
*   يتم وضع هذه الخاصية داخل الكائن التابع لـ `jsonSchema$`، مباشرة بعد كائن الـ `properties`. (سيتم تطبيق هذه الخاصية عملياً في المحاضرة القادمة عند شرح كيفية تحديث المخطط).

---

## **خلاصة المحاضرة (Summary)**
الميزة الكبرى لاستخدام المخطط (**Schema**) على مجموعاتك هي حماية سلامة البيانات. إذا حاول أي شخص إدراج Document غير صالح (**Invalid document**) لا يتوافق مع القواعد المحددة، فإن **MongoDB** ستقوم بحظر العملية فوراً وترمي خطأ التحقق (**Validation Error**)، ولن يتم حفظ الDocument إلا إذا كان مستوفياً لكافة الشروط .
