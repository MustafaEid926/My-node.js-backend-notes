## **آلية اختيار ورفض خطط الاستعلام (How MongoDB Chooses & Rejects a Query Plan)**

## **أولاً: استعراض وتجهيز Indexes في البيئة العملية**

لقياس واختبار كيفية اتخاذ قاعدة البيانات لقرارات الاختيار، نبدأ باستكشاف الIndexes الحالية على الCollection المستهدفة.

### **1. التحقق من ال Indexes الحالية (Checking Existing Indexes)**
قبل البدء، يجب فحص الIndexes النشطة على Collection المستخدمين والتي تحمل اسم **`users`** (مع مراعاة كتابة الاسم بالجمع `users` وليس المفرد `user` لتجنب الأخطاء البرمجية). نستخدم دالة **`()getIndexes`** لاستعراضها:

```javascript
db.users.getIndexes()
```
*   **نتيجة الاستعلام:** كشفت الدالة عن وجود indexين نشطين مسبقاً:
    1.  الindex الافتراضي التلقائي المنشأ على حقل المعرّف الفريد (**`id_`**).
    2. `‏`  index بسيط أحادي منشأ على حقل العمر (**`Age`**) ويحمل الاسم `age_1`.

### **2. إضافة فهرس مركب مخصص (Creating a Compound Index)**
نريد الآن إنشاء فهرس مركب (**Compound Index**) يدمج حقلي الجنس والعمر معاً. 

*   **قاعدة ترتيب الحقول (Field Ordering Rule):** عند تصميم الCompound Index، فإن ترتيب ذكر الحقول بالغ الأهمية ويحدد حالات استخدامه.
    *   إذا أنشأنا الindex بالترتيب التالي: **`{ Gender: 1, Age: 1 }`** (مع مراعاة حالة الأحرف الكبيرة للحقول والترتيب التصاعدي):
        *   يمكن استخدام الindex عند التصفية بحقل الجنس (`Gender`) وحده.
        *   يمكن استخدام الindex عند التصفية بحقلي الجنس والعمر (`Gender` و `Age`) معاً.
        *   **لا يمكن** استخدام هذا الindex عند التصفية بحقل العمر (`Age`) وحده.
    *   **تجنب التعارض والارتباك الهندسي:** إذا عكسنا الترتيب ووضعنا العمر أولاً `{ Age: 1, Gender: 1 }`، فعند الاستعلام بحقل العمر وحده، سيواجه محرك **MongoDB** ارتباكاً وحيرة حول ما إذا كان يجب استخدام الindex الفردي القديم `age_1` أم الindex المركب الجديد؛ لأن كلاهما يبدأ بالعمر. لتجنب هذا التكرار غير المفيد هندسياً، نعتمد الترتيب: الجنس أولاً ثم العمر.

**الكود البرمجي لإنشاء الindex المركب:**
```javascript
db.users.createIndex({ Gender: 1, Age: 1 })
```
*(تم إنشاء الindex بنجاح وحمل تلقائياً الاسم المدمج `gender_1_age_1`)*.

## **ثانياً: دراسة حالة الاستعلام المقارن (The Query Comparison Case)**

### **1. سيناريو الاستعلام**
نريد البحث عن الDocumentات التي تتطابق مع الشروط التالية: الجنس هو ذكر (**`MALE`**) والعمر أكبر من أو يساوي 50 عاماً.
*(ملاحظة: تذكر مطابقة حالة الأحرف الكبيرة في الحقول والقيم مثل `MALE` كما هي مخزنة في قاعدة البيانات)*.

**كود الاستعلام التحليلي:**
```javascript
db.users.find({ Gender: "MALE", Age: { $gte: 50 } }).explain()
```

### **2. الخيارات المتاحة أمام المحرك (Query Execution Options)**
عند تشغيل هذا الاستعلام، يجد محرك **MongoDB** أمامه خيارين (indexين) مؤهلين لتلبية الطلب:
*   **الخيار الأول:** استخدام الindex الفردي على العمر **`age_1`**.
*   **الخيار الثاني:** استخدام الindex المركب الجديد **`gender_1_age_1`**.

## **ثالثاً: تحليل مخرجات خطة التنفيذ (Winning vs. Rejected Plans)**

عند تحليل الاستعلام باستخدام دالة التفسير `explain()`، تظهر النتائج انقساماً صريحاً بين الخطط:

```json
{
  "queryPlanner": {
    "winningPlan": {
      "stage": "IXSCAN",
      "indexName": "gender_1_age_1"
    },
    "rejectedPlans": [
      {
        "stage": "IXSCAN",
        "indexName": "age_1"
      }
    ]
  }
}
```

### **1. الخطة الفائزة (Winning Plan)**
اعتمد المحرك إجراء مسح للindex (**Index Scan / IXSCAN**) باستخدام الindex المركب **`gender_1_age_1`**.
*   **السبب الهندسي للفوز:** نظراً لأن الاستعلام يفلتر بالاعتماد على حقلين معاً (الجنس والعمر)، فإن الindex المركب المبني عليهما يضمن تصفية البيانات بشكل أسرع وأكثر كفاءة، مما يقلل من حجم البيانات المسترجعة بشكل مباشر.

### **2. الخطة المرفوضة (Rejected Plan)**
تم رفض مسار تنفيذ مسح الindex (**Index Scan**) الذي كان سيعتمد على الindex الفردي **`age_1`**، ووُضع في قائمة الخطط المرفوضة.

## **رابعاً: هندسة سباق التقييم (How the Race of Approaches Works)**

كيف يتوصل المحرك بذكاء وعلمية إلى معرفة الخطة الأسرع ويرفض الأخرى؟

### **1. آلية السباق (The Race Mechanism)**
*   عند وجود خيارات متعددة، لا يعتمد المحرك على التخمين، بل يقوم بإجراء **سباق عملي (Race of approaches)** بين كافة Indexes المؤهلة.
*   **شرط الفوز الفعلي (The Winning Condition):** لا يقوم المحرك بتطبيق السباق على كامل مجموعة البيانات لتجنب إهدار الموارد. بدلاً من ذلك، يضع شرطاً نموذجياً مصغراً وهو: **الوصول إلى أول 100 Document مطابق (First 100 documents)**.
*   يقوم المحرك بتشغيل الاستعلامين في نفس الوقت بشكل متوازٍ، والindex الذي ينجح أولاً في جلب واستخراج أول 100 Document مطابق يُعلن فوراً كـ **خطة فائزة (Winning Plan)**، ويتم إيقاف الخطط الأخرى ونقلها إلى قائمة **الخطط المرفوضة (Rejected Plans)**، ثم تُستكمل بقية عملية القراءة للمجموعة بالكامل باستخدام الindex الفائز.

## **خامساً: آلية التخزين المؤقت للخطط وصلاحيتها (Query Plan Caching)**

إجراء سباق تقييم مع كل استعلام يتم تشغيله سيؤدي إلى تدهور أداء النظام بشكل عام. لتفادي هذا، تتبع **MongoDB** استراتيجية كفاءة ذكية.

### **1. التخزين المؤقت (Caching)**
بمجرد انتهاء السباق وتحديد الخطة الفائزة لاستعلام معين، يتم **حفظها وتخزينها مؤقتاً (Cached)** في الذاكرة.
*   **شرط التطابق الصارم لتفعيل الكاش:** لكي يتم جلب الخطة الفائزة مباشرة من الكاش في المرات القادمة وتجنب إعادة السباق، يجب أن يكون الاستعلام اللاحق **مطابقاً تماماً (Exact Query)** للاستعلام الأصلي من حيث:
    1.  اسم المجموعة (**Collection Name**).
    2.  معايير الفلترة والتصفية (**Filter Criteria**).
    3.  الحقول المحددة في الإسقاط (**Projected Fields**).
*   **ملاحظة برمجية:** حتى لو كان الاختلاف طفيفاً جداً (مثل تغيير القيمة الرقمية لشرط العمر)، فإن المحرك سيعتبره استعلاماً جديداً تماماً ويقوم بتشغيل سباق جديد لتحديد خطة فائزة مخصصة له وكاش جديد.

### **2. متى يتم مسح وإلغاء صلاحية الكاش؟ (Cache Invalidation)**
تدرك قاعدة البيانات أن حجم وهيكلية البيانات تتغير باستمرار، لذا لا يتم الاحتفاظ بالخطط المخزنة مؤقتاً للأبد. يتم مسح وإلغاء صلاحية الكاش الفائز فور حدوث إحدى الحالات المعمارية التالية:
*   **تجاوز حد الكتابة (The 1,000 Write Threshold):** إذا تم إدراج أو تعديل أو كتابة عدد معين من الDocumentات داخل المجموعة (الحد الحالي هو **1,000 Document**)، يتم مسح الكاش تلقائياً؛ لأن التغير الكبير في حجم البيانات قد يجعل الخطة القديمة غير صالحة أو لم تعد الأسرع.
*   **إعادة بناء Indexes (Rebuilding Indexes):** عند حذف index موجود أو إعادة بنائه.
*   **إضافة فهارس جديدة (Adding New Indexes):** عند إنشاء index جديد على المجموعة، يتم مسح الكاش لفتح المجال لإجراء سباق جديد قد يثبت فيه الindex الجديد تفوقه وسرعته.
*   **إعادة تشغيل الخادم (Server Restart):** يتم إفراغ الذاكرة العشوائية بالكامل وبالتالي مسح كافة الخطط المخزنة مؤقتاً.

## **سادساً: استخراج إحصائيات الخطط التفصيلية (All Plans Execution Stats)**

إذا رغب مهندس قاعدة البيانات في مراجعة الأرقام التفصيلية والإحصائيات الخاصة بالخطة الفائزة وكافة الخطط المرفوضة جنباً إلى جنب للتحليل الهيكلي، يمكنه تمرير وسيط مخصص لدالة التفسير.

### **الصياغة البرمجية لتفصيل الأداء**
نقوم بتمرير الوسيط **`"allPlansExecution"`** لدالة التفسير لفتح سجلات الأداء الكاملة:

```javascript
db.users.find(
    { Gender: "MALE", Age: { $gte: 50 } }
).explain("allPlansExecution")
```
*(ملاحظة: يجب التأكد من كتابة التعبير بدقة `"allPlansExecution"` لتفادي الأخطاء الإملائية والبرمجية أثناء التشغيل)*.

### **أبرز المؤشرات المستخرجة للتحليل (Metrics Analyzed)**
عند تشغيل هذا الأمر، يعرض الخادم بيانات إحصائية دقيقة لكل خطة على حدة، مما يتيح لك كمطور الاطلاع على:
*   **عدد الDocumentات المفحوصة (totalDocsExamined):** عدد السجلات الفعلية التي زارها المحرك أثناء فحص الخطة.
*   **عدد المفاتيح المفحوصة (totalKeysExamined):** كم عدد المؤشرات التي تمت قراءتها داخل بنية الindex نفسه.
*   **الوقت التقديري للتنفيذ (executionTimeMillis):** الوقت المستغرق الفعلي لإنهاء العملية بالملي ثانية.

تمنحك هذه المؤشرات التفصيلية رؤية كاملة تمكنك من اتخاذ قرارات حاسمة حول الإبقاء على فهارس معينة أو التخلص منها بناءً على تقييم أدائها الفعلي داخل النظام.
